# Payments

Payment processing is the movement of value from a payer to a payee through a sequence of controlled states. A reliable payment system separates the customer request from authorization, capture, settlement, notification, reconciliation, and exception handling.

## Core Payment Concepts

- **Payer:** The customer or account providing the funds.
- **Payee:** The customer, merchant, or account receiving the funds.
- **Authorization:** Confirmation that the payment method can fund the transaction.
- **Capture:** The instruction to finalize an authorized amount.
- **Settlement:** The movement and final posting of funds between accounts or institutions.
- **Refund:** Returning a completed payment to the payer.
- **Reversal:** Cancelling or undoing an authorization or in-flight transaction before final settlement.
- **Reconciliation:** Comparing internal records with processor, bank, or ledger records.

## Typical Payment Lifecycle

```text
Initiated -> Pending -> Authorized -> Captured -> Settled
                 |          |            |
                 v          v            v
              Failed     Declined      Reversed

Settled -> Partially Refunded -> Refunded
```

The exact states vary by provider, but each state should have a clear meaning and permitted transitions. A payment should not move directly from an untrusted client request to a settled state without the required authorization and posting steps.

## Payment Request Design

A payment request should contain:

- A client-generated idempotency key.
- A unique payment ID generated by the payment service.
- Amount represented in the smallest currency unit, such as kobo or cents.
- Currency and payer/payee identifiers.
- A clear description or reference.
- The requested operation and creation timestamp.
- Correlation information for tracing across services.

Amounts should be represented as integers or decimal values with explicit precision. Floating-point arithmetic should not be used for financial calculations.

## Idempotency and Retries

Payment creation, capture, refund, reversal, and posting operations must be safe to retry. A timeout does not prove that the operation failed; the request may have succeeded while the response was lost.

- Require an idempotency key for every operation that creates or changes financial state.
- Store the key with the operation, request fingerprint, final status, and response.
- Return the original result when the same key is received again.
- Reject reuse of a key with a different amount, currency, payment ID, or operation type.
- Use provider references to avoid submitting the same operation twice downstream.
- Make database writes and ledger entries atomic where possible.

## Failure Handling

Payment failures should be classified rather than treated as one generic error.

- **Validation failure:** The request is invalid and should not be retried unchanged.
- **Decline:** The payment method or institution rejected the transaction; the customer may need to choose another method.
- **Transient provider failure:** Retry according to a bounded backoff policy.
- **Timeout or unknown outcome:** Query the provider or reconcile before attempting a new financial operation.
- **Internal processing failure:** Preserve the payment record and retry from the last safe step.
- **Duplicate request:** Return the existing payment result rather than creating another payment.

Never automatically retry a payment operation just because the client did not receive a response. First determine whether the original request reached the provider or ledger.

## Ledger and Reconciliation

The payment record and the accounting ledger should be treated as separate concerns. The payment record describes the workflow; the ledger records the financial effect.

- Record immutable transaction and provider references.
- Keep an audit trail for state changes, actors, timestamps, and reasons.
- Ensure debits and credits balance for every settled movement.
- Run scheduled reconciliation against provider statements or settlement files.
- Investigate unmatched, duplicated, missing, or incorrectly valued entries.
- Do not silently overwrite financial records; use compensating entries for corrections.

## Notifications and Webhooks

Payment status updates are commonly delivered through webhooks. Consumers must authenticate webhook requests, validate the event, handle duplicate delivery, and tolerate out-of-order events. The payment service should remain the source of truth when an event conflicts with a queried payment record.

Notifications should not be the only mechanism that changes a payment state. A missed webhook must be recoverable through polling, replay, reconciliation, or an operational repair workflow.

## Security and Compliance

- Use TLS for all payment traffic.
- Authenticate and authorize every payment operation.
- Never log full card numbers, security codes, credentials, or unnecessary personal data.
- Encrypt sensitive data at rest and in transit.
- Apply least privilege to payment and ledger services.
- Use audit logs that cannot be altered without detection.
- Validate currency, amount limits, account ownership, and beneficiary details.
- Protect against replay, tampering, duplicate submission, and race conditions.

## Operational Checklist

- Every payment has a unique internal ID and provider reference.
- State transitions are explicit and validated.
- Mutating operations require idempotency.
- Unknown outcomes have a query and reconciliation path.
- Retries are bounded, observable, and safe.
- Webhook delivery is authenticated and deduplicated.
- Ledger entries are balanced and immutable.
- Metrics cover success, decline, failure, latency, retry, and reconciliation rates.
- Alerts exist for stuck payments, settlement mismatches, and unusual duplicate activity.
